# Ledger

Severity is high, medium or low. Each line names the rules it sets against each other and where to look.

## Confirmed

- [x] **high, performance**: `item_reference_collects_files` scans every bodiless item for each reference deleted. With no statistics (§9.3's assumption) its `DELETE FROM items WHERE object_hash IS NULL AND (… link_id = OLD.…)` plans `SEARCH items USING INDEX items_by_object (object_hash=?)`, i.e. every `Meta` and released row, and it fires for every reference, `sender` ones included, whose kinds are not files. Measured: 2,000 reference deletes over 100,000 header-only mails take 9.9 s, 3 ms with the trigger dropped; with `ANALYZE` the plan seeks `items_by_link`. Every `collect_before`, `purge_retained_before`, `delete_collection` or bulk `remove_reference` over mail with references pays it under the owner's write lock, and Android's windowed store is exactly the many-bodiless-rows case. Fix: a `WHEN OLD.from_kind = 'application/octet-stream' OR OLD.to_kind = 'application/octet-stream'` clause, and `+object_hash IS NULL` (or `INDEXED BY items_by_link`) so the seek is kept; a plan scenario in invariants.sh as the other seeks have. Pointer: migrations/storage/0001_init.sql, the trigger. Closed by cairn/log/2026-10-10-audit-answered.md (`WHEN`, link-id seek, `+object_hash`), guarded by the two trigger-plan scenarios.
- [x] **medium**: a `part:` key built on a writer-derived message key conflates two messages. §9 and §9.1 say `alt:` and `dup:` keys carry no identity and never share a `seq`; A.7 builds `part:<message link id>#<section>` and §9.1 has it share a `seq` "as a hint does", and §14.2 makes an endpoint a kind and a link id store-wide. Reproduced: two unrelated messages under `alt:Alert|2026-08-01T10:00:00Z|cron@host` in work/INBOX and work/Archive (§9's own example) need one stand-in each under the same key in work/Attachments; the second `insert_item` fails on the primary key, the second `attachment` reference records nothing, `list_attachments` answers the first message's a.pdf for both, and after the first message's purge its stand-in and reference stay, held by the unrelated twin. io-pimdir's `insert_item` (src/client/write.rs, the `derived` prefixes) shares the `seq` of `part:alt:…`. The same conflation holds for any reference whose endpoint is an `alt:` or `dup:` key (`linked:`, the sender and invitation rules). Fix: give a part of a message under a writer-derived key no stand-in (or key it on the message's `seq`, which is per item), and treat `part:` over `alt:`/`dup:` as derived in §9.1; state in §14.2 that a writer-derived key names one endpoint per placement or none. Closed by cairn/log/2026-10-10-audit-answered.md: a writer-derived key is no endpoint (`CHECK`s, statement filters, no stand-in), guarded by "reference: a writer-derived key is no endpoint" and "auto: a deleted mail, and one under a derived key, refer to nobody".
- [x] **medium**: `collect_before` drops a person's references. §11.3 calls the collection lossless ("not a delete", "the remote keeps every member, which a later widening lists and names again"), but `items_drop_references` takes every reference of the last row it deletes, `user` ones included, and a reference is a fact "recorded once, never derived" that no relisting restores. Reproduced: a `related`/`user` reference from a collected mail is gone after `collect_before`. §1's "Un-pushed local mutation is the one thing only the database holds" is now stale too. Fix: count an endpoint of a `user` reference as owing something in `collect_before` (one more `NOT EXISTS`), and name person references beside unpushed mutation in §1. Closed by cairn/log/2026-10-10-audit-answered.md, guarded by "collect: a mail a person's reference names, from either end, stays".
- [x] **medium**: undated mail is in every scope and below every floor. SYNC §5 keeps a message with no usable `date` in every scope ("rare, small and never lost: a draft before sending, a server's own notice"); `:since` (§14.1) and `release_before` (§11.4) put `''` below any date. So a reader listing with a floor never shows mail its sync deliberately keeps, and every `release_before` with any `until` strips the body of a synced undated draft or notice, which no windowed upgrade refetches. The since entry's "as it does for a scope's band" names the band round, not the scope. Fix: let the floor admit `''` (a second seek on `sort_key = ''`, a multi-index OR) and have `release_before` keep undated bodies unless `until` is `NULL`, or state the divergence in §14.1 and §11.4 and have readers add the undated count. Closed by cairn/log/2026-10-10-audit-answered.md: the floor semantics kept, the divergence stated in §14.1 and §11.4.
- [x] **low**: `mail_summary.invitation` reconciled onto an existing store is never backfilled. io-pimdir's `reconcile_invitation` (src/client/schema.rs) adds the column only; every held body then reads `NULL`, which A.1 defines with the body as "no part is one", and an immutable message is never re-derived, so no invitation reference is ever recorded for mail held before the reconcile. §6 requires a backfill "where NULL contradicts the existing rows" and names none for this column. Closed by cairn/log/2026-10-10-audit-answered.md (§6 names the backfill) and io-pimdir's reconciling open.

## Plausible

- [x] **low**: the invitation cannot be cleared. A.1 makes `NULL` both "no part is one" (body read) and "without the body", and `upsert_mail_summary` coalesces, so a body replaced under one link id (a retained row revived by an incoming body, §11.1; an `Add` reviving a tombstone, SYNC §7) keeps the old body's invitation and `link_invitations_of` ties the new message to an event it does not name. Fix: clear on a write carrying the body (a bound flag or a separate statement for the body tier), keep on a write without it. Closed, kept as is, by cairn/log/2026-10-10-audit-answered.md: a mail is immutable, a different body under one key is the wrong merge §9 avoids.
- [x] **low**: `release_before`'s propagation guard reads `sources`, which a source gains at its first sync. A second source declared for the account (`capabilities`) but not yet synced on the collection does not hold a body back, and SYNC §9 then never offers it the released items until a `Full` upgrade refetches them. Fix: also keep the body while a declared source of the account has no `sources` row there, or state that a mirror is set up before a release. Closed by cairn/log/2026-10-10-audit-answered.md: stated in §11.4 (a mirror is synced before a release).
- [x] **low**: Annex A.6 says "lowercased whole" without naming the mapping, while A.2 names the Unicode simple mapping, locale-independent, for the sort key. Fix: name the mapping in A.6 (ASCII for the domain after IDNA, simple mapping for the local part) and add a non-ASCII address to summaries.json. Closed by cairn/log/2026-10-10-audit-answered.md: the default full mapping, guarded by summaries.json "card, full lowercase mapping".
- [x] **low**: a person's reference to a UID-less card (`hash:` key) stays on the old key when the card is edited on its server: §9 retains the old item and keys the new one afresh, so the reference is held by the retained row and dropped at its purge. Closed by cairn/log/2026-10-10-audit-answered.md: a `hash:` key is no endpoint, so the case cannot arise.
