# Tasks carry their organisation

Pimalaya Android organises CalDAV to-dos the GTD way (pimalaya/android cairn/changes/gtd) from standard VTODO properties: `PRIORITY`, `CATEGORIES` as contexts, `RELATED-TO;RELTYPE=PARENT` for a project, an `ATTACH` `mid:` URI (RFC 2392) for the mail a task came from. The app reads them off the body at load time. A second consumer (the CLI, an MCP server) listing or searching tasks should not have to, so the store now carries them, and the two links become references `linked:` already follows.

- **STORAGE Annex A.4**: `task_summary` gains `priority` (0 to 9, `NULL` absent or out of range, a `CHECK` refusing the rest), `categories` (a JSON array of every value in document order, split on unescaped commas, decoded), `parent` (the first `RELATED-TO` of type `PARENT`, or with no `RELTYPE`, RFC 5545 §3.2.15's default) and `mid` (the bare message id of the first `mid:` URI of an `ATTACH` or `URL`). An `X-` property stays the body's alone. upsert_task_summary, get_task, list_tasks_page_asc and load_task_summaries carry the four columns. Guarded by summaries.json's new case "todo, organised" (fixture todo-gtd.ics: two `CATEGORIES` properties and an escaped comma, a `SIBLING` relation before the parent, an https `ATTACH` before the `mid:` one), whose columns checks/vectors.py re-derives from the bytes by a second parser; the two earlier task cases state the new columns empty.
- **STORAGE §14.2**: two roles, `parent` and `source`, and their rules, one statement per end on the invitation rule's pattern: `link_parents_of` and `link_sources_of` after a task's summary, `link_parents_to` after a calendar item's write and `link_sources_to` after a mail's, so either end synced first is tied once the other lands. task_summary_by_parent and task_summary_by_mid, partial, are what the `_to` statements seek. Guarded by a scenario in checks/invariants.sh: a live parent and a live mail referenced, none for an end not held, deleted, of another kind or the task itself (a self reference would break the table's own `CHECK`), a person's reference kept, a late end backfilling, a `NULL` link id backfilling all, and each statement's plan; dropping the self or kind test fails it.
- **SEARCH §8**: `status:` (RFC 5545's VTODO set, lowercased), `priority:` (`high` 1 to 4, `medium` 5, `low` 6 to 9, `none`) and `category:` (one value whole, folded as Annex A.2 folds `fn`), all three read from `task_summary` on the attached store, no index change; the first two closed in the grammar (`status-value`, `priority-value`) and refused as `invalid-value` outside it, `category:` taking no wildcard. Guarded by eleven cases in vectors/search/queries.json over a new item 16 (todo-gtd.ics) in the fixture store, three of them refusals checks/vectors.py re-derives; `folder:home/Calendar` and `changed:..1000000000` gain item 16.
- **GUIDE.md** §14 runs the four statements and backfills all eight rules; §15 compiles the three fields to `task_summary`. **OVERVIEW.md** names a task's two references.

The draft number stays draft-04: it is not tagged yet. io-pimdir follows: the four columns in its VTODO derivation, the four rule statements in its owner's write path, the three fields in its query compiler. checks/schema.sh, names.sh, invariants.sh and vectors.py pass.
