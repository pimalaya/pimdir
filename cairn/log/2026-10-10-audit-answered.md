# The 2026-10-10 audit answered, and what the Android owner asked for

Answers cairn/changes/audit-2026-10-10/tasks.md, line by line, and folds in what the Android owner needed for attachments, files and linking. One entry, the rules being interlocked.

- **The collecting trigger seeks** (audit, high). `item_reference_collects_files` fires only for a reference with a file end (`WHEN`), finds the ends by link id (`link_id IN (iif(…), iif(…))` on `items_by_link`) and keeps the body test off `items_by_object` (`+object_hash`). 2,000 `sender` reference deletes over 100,000 header-only mails: 9.9 s before, 6 ms after. Guarded by invariants.sh "file: the collecting trigger seeks the ends' link ids, never every bodiless row" and "reference: the dropping trigger seeks both ends' keys", which read each trigger's statement back from the schema (`trigger_plan`).
- **A writer-derived key is no endpoint** (audit, medium; §9, §9.1, §14.2, §14.3). An `alt:`, `hash:` or `dup:` key names no identity, so a reference naming one, or a `part:` key over one, would tie unrelated items. Two `CHECK`s on `item_reference` refuse them; `add_reference` and the four rules record nothing for them; a message under one gets no stand-in. Keying stand-ins on `seq` was the alternative and was set aside: a `seq` is per item, so the stand-in would no longer be one file across the labels of one message, and the cost of the rule is small, mail without a `Message-ID` and cards without a `UID` being rare and taking no links. Guarded by "reference: a writer-derived key is no endpoint: recorded by nothing, refused by the schema" and "auto: a deleted mail, and one under a derived key, refer to nobody". A person's reference to a UID-less card (audit, plausible) is moot under this rule.
- **`collect_before` keeps what a person's reference names** (audit, medium; §1, §11.3), from either end, since no relisting restores a reference; §1 names person references beside unpushed mutation. Guarded by "collect: a mail a person's reference names, from either end, stays; a rule's reference does not hold one".
- **Undated mail keeps the floor semantics** (audit, medium): a floor is a reader's window, not a scope; §14.1 states the difference and that a reader showing undated mail beside a window lists it apart, and §11.4 that `release_before` frees undated bodies as a window excluding them would. No behaviour change, the windowed app showing undated mail only when the window is all mail.
- **The invitation is backfilled** (audit, low; §6): reconciling `mail_summary.invitation` re-derives it from every held body, then runs `link_invitations_of` over every mail. io-pimdir does it in the reconciling open; the Android owner must too.
- **A missing table reads as empty** (audit, low; §6): a reader of an unreconciled store runs no statement naming it.
- **Mutation survivors** (audit, checks): a deleted contact, event and mail, a person's reference at each rule's end, a calendar item of another kind, a tombstone and kept bases in the release, a second account's and a tombstoned stand-in, a `related` file reference, a from-side reference, and a part restated. The auditor's mutate.sh over 36 mutants of the new statements and triggers, every listed one included, kills all of them.
- **The invitation is never cleared** (audit, plausible; kept): a body replaced under one link id is the same message by identity, a mail being immutable; a different body under one `Message-ID` is the wrong merge §9 already avoids. Recorded, not changed.
- **A mirror is synced before a release** (audit, plausible; §11.4): a source declared but not yet synced on the collection holds nothing back; stated rather than guarded, the guard needing the declared sources of an account per collection.
- **One lowercase mapping** (audit, plausible; A.2, A.6): the Unicode default full mapping, locale-independent, what Rust's `str::to_lowercase`, Java's `toLowerCase(Locale.ROOT)` and Python's `str.lower` do, chosen over the simple mapping A.2 named because the implementations already use it. Guarded by summaries.json "card, full lowercase mapping" (new fixture card-full-lowercase.vcf: a dotted capital I folds to `i` and a combining dot above) and vectors/README.md.
- **`sum_mail` counts messages and takes a `held` chip** (audit, plausible; §14.1): one per `seq` across the set, at its largest stated size; `held` 1 what a release frees, 0 what a download fetches. Guarded by "sum: a message filed in two collections counts once, at its largest size", "held 1 is what a release frees, held 0 what a download fetches" and "a body one placement holds holds the message".
- **A copy or move to another source of a `Meta` row** (audit, plausible) stays open: refusing it needs the engine to know the target's source at mutate time.
- **Stand-in parts** (Android a; §14.3) are exactly those making the attachment mark, `Content-Disposition: attachment`.
- **The attachments collection takes the role `attachments`** (Android b; §14, schema): the role `CHECK` widened for the file kind, the only owner-assigned role, one per account by `collections_by_role`; a store from before reconciles the constraint by §6's rebuild. Guarded by "file: the attachments role marks a file collection, and no other kind takes it".
- **`delete_collection` may skip the recount** (Android c; §14) when `collection_holds_objects` answered false. Guarded by "file: a collection holding no object pointer can skip the recount".
- **`RETURNING` statements run as queries** (Android d; GUIDE §5).
- **New reads and writes** (Android addenda): `list_attachments_by_account` (every stand-in of an account with its message, newest message first, keyset-paged), `delete_unbound_item` (an item no source binds, its hashes returned for `release_pins`), `get_mail_row` (one row by key in the page's shape), `describe_endpoint` (an end's first live placement and title), `search_contacts`, `search_calendar`, `search_files`; `add_reference` now answers the reference standing, new or not, and no row only for an end missing or derived. Guarded by "file: every stand-in of an account with its message, newest first, paged", "file: an unbound file is deleted with the hashes to release, a bound one is its source's", "row: one mail row by key, in the page's shape", "describe: an endpoint's first live placement and its title, whatever the kind", the three "search:" scenarios and "reference: a duplicate records nothing and answers the reference standing".

The Android SQLite floor (audit, downstream) is the app's to settle. draft-04 is not tagged yet, so the number stays.
