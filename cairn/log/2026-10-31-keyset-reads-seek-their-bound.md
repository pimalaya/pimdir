# Store statements and performance: keyset reads seek their bound

Batch 3 of the release audit (cairn/changes/audit-2026-10-31, lines P1 to P8), landing keyset-reads-seek-their-bound with it, so this entry carries that change's id. storage-draft-08, sync-draft-07 and search-draft-08 stay as batch 1 set them. D1's `bindings_by_link` and D4's cheap half land here.

Rules, and the check guarding each. Every check named below was run against the tree before this batch (the working tree after batch 2, copied with `cp -a`) and failed there, unless the line calls it a guard: a guard passes on both trees and fails when the plan or the result it pins regresses. Plans are EXPLAIN QUERY PLAN with no `ANALYZE`, on SQLite 3.50.4 and, where the line says so, on 3.18.2 (checks/floor.sh's build).

A merge reads each collection of the set down to a page under its filters, so a rare match costs each collection its walk where the old global walk stopped at the first page of hits overall: `%alice%` reads a1/Sent whole (its sender is the owner) and `%w1 %` six collections down to fifty hits each. Every other page measured is cheaper, the first pages no longer pass the 251,015 contacts, stand-ins and future events sorting above the newest mail, and a deep page is a seek. The store's `LIKE` search stays the stopgap SEARCH.md's index replaces.

Size, both stores compacted by `VACUUM INTO`: 2,200.2 MB before, 1,940.7 MB after (-259.5 MB, -11.8 %, 204 bytes an item). `item_address` without rowid: table -12.7 MB, its key's autoindex -183.9 MB, `item_address_by_address` +92.9 MB (it now carries the link id and position), net -103.7 MB. `item_reference`: -113.6 MB, its 105.3 MB autoindex gone. `mail_in_reply_to`: -4.4 MB. ## Rules

- **The origin and the destination seek one key** (STORAGE §4.3, §14; P1, D1). `bindings_by_link ON bindings(link_id, source)`. `origin_for_link` also asks for the key a minted form names, `link_id IN (:link_id, CASE WHEN :link_id GLOB 'dup:*' THEN substr(:link_id, 5, (length(:link_id) - 6) / 2) END)`, its exact test kept as the filter: the minted form is `dup:`, the key, `#`, U+0001 and the key again (SYNC §2, GUIDE §9), so the key is the `(length - 6) / 2` characters after `dup:`, and every row the old predicate took is in that set (checked over 13 keys, an empty one, `#`, U+0001, non-ASCII, an already minted key, and 55 probes: no row the old predicate takes falls outside it). `destination_for_link` keeps its text, its two equalities now a seek. Plan `SCAN bindings` and a temporary B-tree become `SEARCH bindings USING INDEX bindings_by_link (link_id=? AND source=?)`, the B-tree sorting the few rows found; the same on 3.18.2. Guarded by invariants.sh, "placement: origin_for_link seeks bindings_by_link, never every binding" and the same for `destination_for_link`, and two guards, "origin: a create keyed by the key minted over its provisional handle pairs with the key's holder…" and "destination: a tombstone pairs with the pending create of its key minted elsewhere".
- **A keyset page seeks its cursor** (STORAGE §9.3; P2). A cursor is coalesced into the row value, `(sort_key, seq) < (coalesce(:after_key, x''), coalesce(:after_seq, 0))` newest first, `''` and 0 oldest first, never tested apart: `:after_key IS NULL OR …` kept it out of the index. The empty blob sorts above every text, the sort key being text by its `CHECK`. In `list_mail_page_desc` and `list_items_page_desc` (plan `items_by_sort (collection=?)` becomes `(collection=? AND (sort_key,seq)<(?,?))`, on 3.18.2 too), `list_held_mail` and `list_held_tasks` (`SCAN … sqlite_autoindex_items_1` becomes `SEARCH … ((collection,link_id)>(?,?))`, a link id never being empty), `list_attachments_by_account`, `list_address_placements` and the merges below. The oldest-first pages already sought `(sort_key,seq)>(?,?)` and keep their text. Guarded by invariants.sh, "page: list_mail_page_desc seeks its cursor on items_by_sort, the first page's too" and the same for `list_items_page_desc`, "derivation: list_held_mail seeks its cursor on the key, the first page's too" and the same for `list_held_tasks`; the six "page: list_…_page_asc seeks its cursor on items_by_sort" are guards.
- **A page over a set of collections is a merge** (STORAGE §4.3, §9.3, §14.1; P2, P4). `list_mail_page_filtered`, `search_mail`, `search_contacts`, `search_calendar` and `search_files` join the set's distinct ids to `items` through `i.rowid IN (SELECT … ORDER BY … LIMIT :limit)`, a correlated subquery seeking that collection's `items_by_sort` beyond the cursor under the page's filters, then order and cut the union, at most the set's size times the page: plan `SCAN i USING INDEX items_by_sort_global` (the mail pages) or a sort of every match (the pickers) becomes a `CORRELATED LIST SUBQUERY` with `SEARCH x USING INDEX items_by_sort (collection=? AND (sort_key,seq)<(?,?))` and a temporary B-tree for the merged page. A collection named twice is read once. `search_calendar` reads one component's summary per item (§14) through three `LEFT JOIN`s in place of its `UNION ALL`. `search_mail` is under the bound and its page capped per collection; a pattern a collection never matches still reads that collection's summaries, which is what a `LIKE` costs. With no reader left, `items_by_sort_global` is dropped: `list_domain_placements` and the search part's `items_to_reexpand` scanned it whole and scan `items_by_sort` now, and `list_attachments_by_account` finds its collection by `collections_by_role` (`ifnull(c.account, '') = ifnull(:account, '')` beside the exact `IS`) and its stand-ins by `items_by_seq` rather than walking every live item. Guarded by invariants.sh, "page: no index orders every kind store-wide", "page: list_mail_page_filtered merges each collection's seek below the cursor, scanning nothing" and the same for `search_mail`, "page: search_contacts merges each collection's seek above the cursor, scanning nothing" and the same for `search_calendar` and `search_files`, "since: the page seeks the floor on each collection's items_by_sort", "file: every stand-in of an account is read from its attachments collection, found by its role, never from every item", and two guards walking pages of two, "page: a page smaller than a collection's share merges the set in order, a collection named twice once" and "search: a page smaller than a collection's share merges the set in order", beside the walks on the synthetic store above.
- **A count reads what it filters on** (STORAGE §14.1; P2). `count_mail`, `count_mail_by_day` and `count_unread` drop their `LEFT JOIN mail_summary` and read the summary through `EXISTS` only when `:attachment` is bound. The proposal's seen test (`instr` on a JSON flag set) is obsolete since flags became rows: every read tests `\Seen` by a seek on `placement_flag`'s key, the same `EXISTS` in each. `sum_mail` keeps its join, which its sizes need. Guarded by invariants.sh, "count: count_mail joins no summary, reading it for the attachment chip alone" and the same for the other two; "count: … tests the read flag by a seek on placement_flag's key" for six statements is a guard.
- **A batch reads its own link ids** (STORAGE §4.4, §14; P3). A read over a whole collection and the same read over a slot's link ids are two statements, the second `_by_link`; `:scoped` and its convention are gone. Plan `SEARCH … (collection=?)` with the `OR` as a filter becomes `SEARCH … (collection=? AND link_id=?)` over the slot, ordered without a sort, on 3.18.2 too. Guarded by invariants.sh, "batch: a summary, the addresses, the reply ids and the categories load for the slot's link ids alone", "batch: the same loads over a whole collection" and nine "batch: …_by_link seeks each link id, never the collection's rows". The harness's `:scoped` binding goes.
- **A purge reads what it purges** (STORAGE §4.3, §11.2; P5). `items_by_retained ON items(retained_at, object_hash) WHERE retained_at IS NOT NULL`: `purge_retained_before` seeks below its cutoff and `retained_bytes` reads the index alone, both formerly `SCAN items`; on 3.18.2 too. Guarded by invariants.sh, "purge: purge_retained_before reads items_by_retained, never every item" and the same for `retained_bytes`, and two guards, "purge: retained_bytes sums each retained body once" and "purge: a cutoff takes the rows retired before it, never a later or a live one, answering their pins".
- **Small rows carry no rowid; a pointer index holds the pointers set** (STORAGE §4.3; P6, D4). `item_address`, `mail_in_reply_to`, `task_category`, `item_reference` and `supersessions` are `WITHOUT ROWID` beside `placement_flag` and `binding_base_flag`: rows of a few short columns, none read by rowid. `item_reference` is not a child table but its rows are keys, a role, an origin and an instant, and its autoindex was the largest single saving. The summaries, `bindings` and `items` keep their rowid: a subject or a summary of any length, secondary indexes that would each carry the key in place of the rowid, or a reader of the rowid. `bindings_by_object`, `bindings_by_shared_object`, `bindings_by_conflict_object`, `items_by_conflict_object` and `queue_by_object` are partial `WHERE … IS NOT NULL`. `items_by_object` stays whole: the search part's `coverage` seeks its `NULL` entries, and a partial one made `coverage` scan `items_by_sort` (0.184 s to 0.781 s on the synthetic store). The program of `DELETE FROM objects WHERE hash = ?`, foreign keys on, opens the six pointer indexes and never `items`, `bindings` or `queue`, on 3.50.4 and 3.18.2 alike; a partial index whose `WHERE` an equality does not imply makes it open `items`. Every plan was diffed against the 230 statements of the tree before: a key read moves from the autoindex to the table's own key, and `list_sources` scans the covering `bindings_by_link` in place of `bindings_by_handle`, at the same cost. Guarded by invariants.sh, "schema: the tables of a few short columns carry no rowid", "schema: a pointer index holds the set pointers alone, but items_by_object, which coverage reads bodiless" and the guard "schema: an object's delete checks every pointer at it on its index, never reading items, bindings or the queue", and by checks/floor.sh, which now reads the same program on 3.18.2 and on the current SQLite and fails unless it opens the six indexes alone.
- **A message's attachments are held by its account** (STORAGE §14.3; P7). `list_attachments`' `object_hash` subquery takes `hc.account IS :account`, so another account's copy of a same-keyed file is never answered. Guarded by invariants.sh, "file: a file another account holds under the same key never reads as held" (before: work's body answered for home's stand-in).
- **The person axis is a page; a day shifts by minutes** (STORAGE §14.1; P8). `list_address_placements(address, role, after_key, after_seq, after_collection, after_role, limit)`: newest first, a keyset page on `(sort_key, seq, collection, role)`, one row per placement and role, its first position there (a `NOT EXISTS` over `item_address_by_address`, so the page's sorter holds `:limit` rows where a `DISTINCT` held every placement of the address). A page reads the address's placements and keeps the newest. `count_mail_by_day`'s `:shift` is the reader's offset from UTC in whole minutes, `120` east and `-300` west, `NULL` UTC, the statement building the modifier itself. Guarded by invariants.sh, "people: an address's live placements, newest first, once per role, paged", "people: a page seeks the address on item_address_by_address, holding no more rows than it answers" and "count: per day, on the reader's clock, its offset in minutes east and west" (before: an integer is no modifier, every day `NULL`).
