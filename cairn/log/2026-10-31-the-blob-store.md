# The blob store

Batch 2 of the release audit (cairn/changes/audit-2026-10-31, lines O1 to O6), on the user's decisions D5, D6 and D9 of 2026-10-31. storage-draft-08, sync-draft-07 and search-draft-08 stay as batch 1 set them for the whole audit. D5 reverses the drop of edit 9 (BLAKE3 alone) that 2026-10-30-every-vocabulary-is-open-or-closed recorded because the Android app creates `sha256-128` stores: drafts being exact (batch 1), those stores are refused and reinstalled anyway.

Rules, and the check guarding each. Every check named below was run twice where it exists: against the tree before this batch (the working tree after batch 1, copied with `cp -a`; invariants.sh with `init_store_meta` bound as that tree's statement needs), and against the finished tree with that one rule removed. It failed both times unless the line says otherwise.

- **One algorithm** (STORAGE §2, §4.3, §5, §13; D5, O2). BLAKE3 at its default 32 bytes is the only digest; `sha256-128` and "MUST NOT be inferred from a name's length" are gone. `store_meta.hash_algo` stays, a closed vocabulary held by `CHECK (hash_algo IN ('blake3'))`, so another algorithm would be a value a migration adds, raising `read_version` (§6). `init_store_meta` writes `'blake3'` itself. Guarded by invariants.sh, "blob: a store names BLAKE3, and no other algorithm" (an update to `sha256-128` succeeded), and by checks/vectors.py through vectors/schema/: objects.json is now `v` 2, its `algorithms` and every case closed to `blake3`, and summaries.json `v` 3, every `body` naming its `blake3` name alone; the files of before fail both schemas (`v`, and `sha256-128` unexpected in 13 cases and 34).
- **A hash is a name, never a path** (STORAGE §5, §13, §15.1, §15.3; O1). `objects.hash` carries `CHECK (length(hash) = 52 AND hash NOT GLOB '*[^a-z2-7]*')`, so every column naming a body holds a well-formed name through its foreign key, `queue.object_hash` included. An implementation MUST check a name against the alphabet and the length before it builds a path from it, wherever it read the name, and MUST NOT follow a symbolic link opening a shard directory or a blob where the platform allows; a link found there holds no body and an owner quarantines it. The collector unlinks only a regular file, by `lstat`, whose well-formed name begins with its shard directory's two characters, the directory itself a well-formed directory and no link, and leaves and reports anything else. The owner reads a queued body from `queue.object_hash`, never from the payload, and MUST park a row whose payload's `object` is not that value. Guarded by invariants.sh, "blob: a name is 52 characters of lowercase base32; ../x, an uppercase, a short, a long, a 1, a padding and a separator are refused" (all eight stored before) and "blob: a producer storing ../x stores, pins and enqueues nothing, so no queued body names a path" (before, a queue row named ../x), and by checks/floor.sh, which now inserts a well-formed name and three malformed ones on SQLite 3.18.2 (before: "objects.hash takes the name [../x]"), so the CHECK is verified to load and to mean the same on the floor. The path rule, the link rule, the collector's walk and the queue's park are program and filesystem behaviour no check here observes; no vector format covers the drain.
- **A write never replaces** (STORAGE §5; D5, O3). The temporary is moved onto the final name by a move that fails when the name exists (`link(2)` then `unlink(2)` of the temporary, `renameat2` with `RENAME_NOREPLACE`, or the platform's), never by `rename(2)`. When the name exists the temporary is discarded and the file there kept, its bytes verified when read; any other failure fails the write. A body streamed to its path (§14) is written the same way. GUIDE §4's "the rename is harmless" is gone. Filesystem behaviour: no check here observes it.
- **Verification** (STORAGE §6 step 2, §7, §15.2; SEARCH §4; O4). A body read whole MUST be verified before it is served, parsed, indexed, pushed, copied or used to perform an intent, a streamed read failing at its end before its consumer commits anything. Whoever serves, parses or copies a range MUST first read the whole file through the same descriptor and verify it, which covers every range read through that descriptor while it is open; nothing is recorded. A body failing its name is missing: an `add` or an `update` carrying it is retried then parked, and a `Full` item holding it is fetched again where a source holds it. An owner MUST move it into quarantine/ (new in §3's layout and §2's terms), under its name, a period and a suffix unique to the move, holding the staging lock exclusively and serialised against its own writers, after verifying again, and MUST NOT unlink it; a reader or a producer moves nothing; nothing reads quarantine/ as bodies, the collector never walks it, only the user empties it. A `hash_algo` a program does not know refuses the store (§6 step 2), never read as corruption. SEARCH's sentence on a body the indexer cannot find now names one failing its name, with no other change to SEARCH. Guarded only in part: the closed vocabulary above makes an unknown algorithm unrepresentable at this draft, and sync vector 94 (a corrupt body is never pushed) stands. The order of verification, ranges, streams and the quarantine move are program and filesystem behaviour no check here observes, and the sync vector format states no blob file after a run, so no vector pins the move.
- **One shard level** (STORAGE §3, §5, §16; D6, O5). `objects/<hash[0:2]>/<hash>`, at most 1,024 shard directories. Guarded by checks/vectors.py, which derives each path as `objects/<name[0:2]>/<name>` and requires every name to be 52 characters of the alphabet: the 13 paths of before fail.
- **Other platforms** (STORAGE §5, §8; D9, O6). §5: on Windows the no-replace move (`MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`, with `MOVEFILE_WRITE_THROUGH`, or `CreateHardLinkW`), no directory flush, a file held open deleted only under `FILE_SHARE_DELETE` (a reader SHOULD open a blob so) with its name taken until the last handle closes, an unlink that fails left to the next collection and a quarantine move that fails to the next read; on macOS `F_FULLFSYNC` for the temporary and the directory, and `renamex_np` with `RENAME_EXCL`. §8: on Windows the lock of a crashed process lingers until the system releases it, the owner failing at once and the caller retrying; on macOS `PRAGMA fullfsync = ON` SHOULD be set beside §4.1's `synchronous`. Platform behaviour: no check; checks/names.sh learns `renamex_np`.

The harness: the schema now refuses the two-character labels invariants.sh used as hashes, so its scenarios name bodies through `name`, a label padded to 52 characters of the alphabet (`$h1` for h1), and the types scenario stores a well-formed name, its blob case cast from one, so the name CHECK does not shadow the type checks it tests. checks/floor.sh's header and summary line say what it now runs.

Statement signatures that moved: `init_store_meta` (`:hash_algo` removed). Vector formats that moved: objects.json `v` 2 (`blake3` alone, one shard level), summaries.json `v` 3 (`blake3` alone per body); vectors/README follows, its anchors now BLAKE3's own test vectors, whose `i mod 251` lengths cover every patterned body.

GUIDE §1 (steps 3, 5 and 11), §2, §3, §4 (now naming, writing and reading a body), §6, §11, §13, §14, §15 and §16, and OVERVIEW §1 follow.

Left: a backup (§8) copies objects/ and not quarantine/, whose files may be the only copy of a body; the Android app, which names bodies by `sha256-128`, follows (the audit's Followers), as does io-pimdir, whose `init_store_meta` binding and vector readers change. `nix flake check path:$PWD` passes.
