# Three store gaps io-pimdir found

io-pimdir's ports and its store-version work (its logs what-the-app-ports-found and the-store-version-contract, 2026-10-30) met three places storage-draft-05 was silent or said two things. Lands in storage-draft-05 itself, no number bump.

- **STORAGE §15.3, an item no source binds** (normative): §15.2's three outcomes left a skip the only reading for every kind but `remove`, a row pending for ever. An owner applies or parks, never skips: `remove` retains the item; in a collection no source syncs (`collection_sources` answering none) `set-flags` and `update` apply to the item directly, `update` on its usual terms, `if_match` included, a body deriving no summary or another key parking it; `move` and `copy` park, a producer filing such an item elsewhere using an `add` with `supersedes`; in a collection a source syncs every other kind parks, the item awaiting its first push and no source binding it to run the mutation as. This is io-pimdir's choice, stated. Guarded by checks/invariants.sh ("unbound: ...": `collection_sources` tells a local collection from one whose source holds only a checkpoint, a set-flags moves the item's stamp, a remove retains it with its body pinned); no check here runs a drain, so the outcome per kind is the implementation's to test, as io-pimdir's tests/unbound_items.rs does.
- **STORAGE §6, the reader of an older store** (normative): a reader or producer reads an older or unreconciled store as its reconciliation would leave it before any backfill, a missing column `NULL`, or its canonical `DEFAULT` where 0001_init.sql declares it `NOT NULL` with one (so `store_meta.derivation` reads 1 and `task_summary.categories` as none), a missing table empty; it runs a canonical statement naming a missing column with each mention replaced by that value, its name, parameters and result columns kept (§4.4), and answers no row for a missing table. What it means is stated: no role, a coverage never closed (filling, never complete), invitations and task organisation unknown. Guarded by checks/invariants.sh ("reader: ...": the canonical `list_coverage` and `load_store_meta` fail as written on an earlier draft's `sources` and `store_meta`, and the substituted text answers the source with a coverage never closed and the revision 1).
- **STORAGE §6, pimdir.db holds the canonical schema alone** (normative): one rule, stated once. A table, column, index or trigger 0001_init.sql lacks is dropped by the reconciliation of a version 1 store; an implementation keeps state of its own outside the store directory (§3), never in pimdir.db; a newer owner adds only by a migration to a later version, which an older owner refuses before reconciling (step 1); after the release a version 1 store holds 0001_init.sql's objects and its owner's open reconciles nothing. Steps 2 and 3 now say so (a column the canonical text lacks goes with the old table; step 3 drops tables too, not only indexes and triggers). The other reading, an owner keeping what it does not know, was dropped: the reconciliation test is the schema text, which a kept extra never matches, so every open would rebuild around it, and a kept table escapes the refcount floor and the migration rule. This contradicts io-pimdir's dropped task "a store carrying a table or column this crate does not know keeps it through an owner open" (cairn/changes/the-store-version-contract/tasks.md there), which io-pimdir already settled the same way. Guarded by checks/invariants.sh's reconcile scenario, which now adds another implementation's table and column, finds both differing, and finds neither after the rebuild and step 3.
- **GUIDE §2, §13** (informative): the reader's substitution; the drain's outcomes for an unbound item.

`nix flake check path:$PWD` passes. io-pimdir follows in its cairn: its `apply_unbound` applies an `update` without checking `if_match`, which §15.3 requires there as anywhere; its `list_coverage` answers no row on a store lacking the coverage columns, which reads every collection as complete where this rule reads its sources as filling; its `NULL` for a missing `categories` reads the same as the `'[]'` default.
