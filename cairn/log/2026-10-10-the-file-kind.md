# Files, and attachments that stand for a message's parts

The Android plan's Part C step 2: a file kind beside mail, contacts and calendars, shaped by what attachments need (C.3), so a message's attachments list, open and save without copying their bytes out of the message.

- **The kind is `application/octet-stream`** (§14.3). Every other kind names its stored object's media type, and a file's object is bytes of any type; the file's own type lives in its summary. A bespoke `x-` type was the alternative, and would have named nothing the body is. Guarded by invariants.sh "file: a blob-less file is a Meta item with its summary" and "a folder lists A to Z on the name".
- **`file_summary`** (Annex A.7, §4.3), one row per placement: `name` (so a rename is a summary write and one file may carry two names in two folders), `media_type`, `size` (the body's octets once held, as for mail) and `part`. Not derived from the body, which states nothing; stated by the source or the writer. `sort_key` is the name on the card's rule. Statements `upsert_file_summary`, `load_file_summaries`, `list_files_page_asc`, `get_file`; names.sh expands `<kind>` to `file` too.
- **The part id is a summary column**, not a payload on the reference. An attachment item is one part of one message by construction (its key is derived from both), so the part is a property of the item; a reference stays a bare relation with no column only one role would use, and opening an attachment reads one row. Guarded by "file: a message's attachments in the order recorded, with their part".
- **Keys** (Annex A.7, §9.1): `part:<message link id>#<section>` for an attachment, so every writer walking one message names its files alike, and `file:` with 128 random bits for a file created in the store. They are names the store gives, not guesses, so they share a `seq` across collections as a hint does: a stand-in and its saved copy show once. Guarded by "file: one public id for the stand-in and the saved copy" (the sharing itself is the writer's, io-pimdir's insert_item already keying only `alt:`, `hash:` and `dup:` apart). Keys for files a source lists wait for the first file source.
- **Attachments live in a file collection of their account that no source syncs** (§14.3), the owner choosing it: an item needs a collection, the message's own holds another kind, and per account keeps an account's removal whole and one stand-in per part even when Gmail files the message under several labels. No role marks it: one would have meant rebuilding `collections` to widen the role `CHECK` in every store, and the collection rule below needs none. A source-less collection's items carry no binding, which §11 never retains and no projection offers.
- **A blob-less stand-in is valid and claims nothing**: `object_hash` `NULL`, `level` 1, its summary present, which SYNC §6 already reads as no claim; nothing syncs its collection.
- **A stand-in goes once no reference names it**, by `item_reference_collects_files`, a trigger on `item_reference` deletes, matching the earlier choice of a trigger over a sweep: a file of the kind holding no body and bound by no source, with no reference left either way. A message gone with its last row drops its references (items_drop_references), which drops its stand-ins; a saved copy holds a body and stays. The owner records the stand-in and its reference in one transaction, the trigger acting on deletes only. Guarded by "file: a stand-in no reference names is collected", "a file holding a body, or bound by a source, is never collected for want of a reference" and "the message's last row gone, its stand-in goes and the saved copy stays with its body"; each fails with the trigger, its binding test or its body test removed.
- **`list_attachments(account, link_id)`** reads a message's files through its `attachment` references, one row per file, the stand-in's summary preferred and any placement's body as `object_hash`, in `seq` order, which is document order for a writer walking the parts in it (a section's text order is not, `10` sorting before `2`). Guarded by "file: saved to a folder, the stand-in still reads, held by the saved copy's body".
- **A file is mutable** (SYNC §5): a folder's connector MUST report revisions, and the existing base and conflict carry edits; nothing kind-specific is added. No sync vector until a file connector exists to define a member's meta.

The trigger chain (a purge firing items_drop_references, whose delete fires item_reference_collects_files, whose delete would fire items_drop_references again) relies on that inner firing finding nothing to drop, which holds with `recursive_triggers` off, SQLite's default, or on. draft-04 is not tagged yet, so the number stays.
