## Rules and their checks

Each line names the ledger id, the rule, where it is stated and the check that fails without it. A rule no check of this repository can hold says so: the repository runs SQL and reads JSON, and holds no blob directory, no lock and no connector.

- **X1, what a name binds** (decided Q6; STORAGE §4.4, §5, §14, §17; GUIDE §1; OVERVIEW §1, §11; README). A canonical name binds the text run under it: the name, its parameters, its columns in order and its effect. An implementation may reach a section's effect through statements of its own, under names of its own, bound by §7's invariants, the rule that a statement names its columns, the rules stated for that effect and the vectors; "an operation runs a statement" describes the reference form. Once released, a statement added is a minor version, a signature changed a minor at least, a statement removed a minor that lists it. The collector's step, `write`'s head and `DeliverPlacement` no longer say a statement is run where the effect is what binds, and §17 asks for §4.4's terms rather than for running the directories. Check: none can tell an implementation's statements from here; checks/names.sh still holds every name a document writes, and checks/frozen.sh (the other entry) holds a released signature row.
- **X2, one wording** (STORAGE §9, §10, §14, §15.2; SYNC §4). The rebind sentence of §14 names a `Superseded` or `Rekeyed` drop, as §10 does. `SHALL` and `SHALL NOT` are `MUST` and `MUST NOT` in the six sentences that carried them. Check: checks/names.sh fails on a `SHALL` in any part outside the sentence naming the key words.

- **F13, three vocabularies said open** (STORAGE §13). `item_address.role`, `dtstart_value` and `due_value` are open. A reader reads a row of an unknown role as naming its address in no role, still answered where a read asks for any; it does not interpret a `dtstart` or a `due` under an unknown value type, reading the property from the body where it holds one and otherwise showing no time. - **F14, one name for the owner** (decided Q11; STORAGE §3, §6, §8, §18; OVERVIEW §1). The store directory reserves the subdirectory local/ for an owner's own state, created `0700`, never defined, ignored by readers and producers, never walked by the collector, copied by a backup; an implementation keeps its state under it or outside the store directory, and no other file of its own beside it. - **F16, a lock file stays, and the unconfirmed intent** (decided Q9; STORAGE §8, §13, §15.2, §15.4, §15.5, Annex B.2; GUIDE §1, §13; OVERVIEW §8). A lock file is never removed, renamed nor replaced while the store exists, and an owner should verify before a write transaction that the file it holds locked is still the one at the path. An intent whose outcome is unknown is parked under an `error` beginning with `unconfirmed: `, the one reserved prefix of `queue.error`; no drain retries it; it leaves that state confirmed by its performer (acknowledged with its receipt), retried on a person's request, or withdrawn. `submit` alone ends so. The new statement **`retry_action(id)`** puts a parked row back among the pending ones, its error cleared, its id and attempts kept, answering the id, and nothing for a row pending or gone. Checks: the scenarios "unconfirmed: ..." and "retry: ..." of checks/invariants.sh (seven assertions); queries/signatures.json restated; checks/names.sh for the name. The lock sentence has no check here.
- **F17, several actions in one transaction** (decided Q13; STORAGE §15.1, §15.2; GUIDE §13; OVERVIEW §8). A producer may enqueue several actions in one transaction, all or none, in the order enqueued. An owner may apply a bounded run of pending actions in one transaction, each under a savepoint, claim first; a failed apply is rolled back before anything else, its transaction or in a run its savepoint alone, and the park or the retry is recorded after that rollback, outside the savepoint. Exactly once and the append order stand. Checks: "enqueue: several actions in one transaction ..." (one refused, none appended; three appended in order) and "run: ..." (a run not committed applies none; in a committed one the failed action is restored and parked, what it wrote undone, the two around it applied with their receipts).
