# Four search gaps io-pimdir found

io-pimdir's query-only index (its log a-query-only-index, 2026-10-30) met four places search-draft-05 left to the implementation. Lands in search-draft-05 itself, no number bump.

- **SEARCH §2, migrations/search/0001_init.sql** (normative, index schema): while the part is a draft its schema is folded into 0001_init.sql at version 1, so an index an earlier draft built is told by its shape, compared as STORAGE §6 compares a store's (each table, index and trigger 0001_init.sql creates by name, FTS5's shadow tables and an implementation's own tables left out), and rebuilt. The index is derived, so a rebuild is the whole reconciliation. Guarded by checks/schema.sh applying the schema and by the scenarios below, which fail on the old schema.
- **SEARCH §4, `index_meta.store_reconciled`, `set_index_cursor`, `load_index_meta`** (normative): the store_change of the last completed pass, which a batch never moves; a collection's stamp is compared with it, never with `store_change`. Before it a deadline-cut pass whose batches folded a rename's restamped items moved `store_change` past the collection's stamp, and the next pass never reconciled the old placements. A canonical column rather than io-pimdir's private `index_build.reconciled`: the cursor a pass resumes from is canonical, so the stamp deciding whether it reconciles must be too, else a second indexer resuming a cut pass misses the rename the first one skipped. A batch-time reconciliation needing no column was weighed and dropped: it runs `placements_gone` once per collection stamp a pass crosses, where the column costs one per completed pass. `set_index_cursor` binds `:store_reconciled`, `load_index_meta` answers it last. Guarded by checks/invariants.sh ("reconciled: past a batch, the collection's stamp lies above store_reconciled and not above store_change"), which fails on the old schema.
- **SEARCH §6, §8, `object.attachment`, `insert_object`, `attached`** (normative): the extraction records whether it wrote any text into the `attachment` field, and `has:attachment` reads a calendar item by `attached`. io-pimdir decoded the field's token count from `object_text_docsize` through a registered function, which ties every implementation to FTS5's shadow-table format and to a function of its own; the column is a seek any SQLite reads. Non-empty text is the test, as §8 already worded it; a token count differs only on a `FILENAME` of punctuation alone with no `FMTTYPE`. Guarded by checks/invariants.sh ("attached: ...", failing on the old schema) and by the existing cases `has:attachment` and `has:attachment kind:task`.
- **SEARCH §8.2, `behind`** (normative): the coverage states how far the index lags the store, store-wide: the stamps the store drew above `index_meta.store_change`, zero exactly when every change is folded, else an upper bound on the rows left to fold. It is io-pimdir's `behind` (head stamp minus the index cursor). Guarded by checks/invariants.sh ("behind: ...", failing without the statement).
- **SEARCH §8 `id:`** (vectors only, no rule moved): store.json gains item 24, a file whose source states the id 4, and queries.json the cases `id:4` (the contact of seq 4 and the file of link id 4) and `id:24` (the seq alone); the cases negating every other kind, `changed:..1000000000` and the name sort gain item 24.
- **GUIDE §15, OVERVIEW §10** (informative) follow.

`nix flake check path:$PWD` passes, checks/names.sh with it (`attached`, `behind`). io-pimdir's tests/search.rs `every_search_vector_answers` passes on the new cases. io-pimdir follows in its cairn: re-vendor the schema and the statements, `store_reconciled` in place of `index_build.reconciled`, `attached` in place of the docsize function, and the shape test. Its own `index_build` table may stay, the shape test leaving it out; rebuilding every index that lacks it, one another implementation built, is allowed (the index is rebuilt at will) but costs a full extraction whenever two indexers alternate on one store.
