# The consumers' gaps fold into draft-08

io-pimdir and the Android app, the first programs on storage-draft-08 and sync-draft-07, met six places the documents were silent, said one thing two ways or bound what a platform cannot do (io-pimdir cairn/log/2026-11-01-a-truncated-message-walks-alike.md and 2026-11-01-a-person-settles-an-item-conflict.md; android cairn/log/2026-11-01-the-shape-follows-storage-draft-08.md). Lands in storage-draft-08 and sync-draft-07 themselves, no number bump, as the user decided on 2026-11-01: neither is tagged, none of the six touches the schema, and a new number would force every store to be reinstalled. checks/tags.sh reads both as "no tag yet" and lets their files move (cairn/changes/the-consumers-gaps-fold-into-draft-08).

Rules, and the check guarding each:

- **How a line of a message ends** (STORAGE Annex A.1, normative). A line, in a header block or a multipart body, ends at CRLF, a bare LF or the end of the message; one `\r` just before the end is the line break's, so a closing delimiter cut between its `\r` and `\n` still closes its multipart and a header line cut there drops it; any other lone `\r` is the line's content, so a header line holding one before its CRLF (raw `\r\r\n`) is no empty line and the block goes on; content read as octets keeps every octet. The header bullet points at the rule instead of stating line ends for the header block alone, and the revision 3 paragraph names it. Guarded by three summaries cases, each with its fixture: "mail, a closing delimiter cut before its line feed" (mail-cut-delimiter.eml: mark 1, the stand-in 6 octets, where the `\r` read as content leaves either no part or one of 15 octets), "mail, a header line holding a lone CR" (mail-stray-cr.eml: the Subject and Message-ID after the line read) and "mail, a header cut after its CR" (mail-header-cut.eml: subject `Cut short`). checks/vectors.py's header path reads a final `\r` as the rule says; it failed on the third case before (`Cut short\r`). Its mark and stand-in path, the stdlib walk, ends a line at every lone `\r`, so the stray `\r` case sits at depth 0 before fields the walk does not read (the change's tasks.md keeps that open).
- **Annex A stays at revision 3.** The rule changes what a writer derives only from a message holding a lone `\r` or cut after one, and io-pimdir's `derive`, which writes the rows of every store draft-08 has (the Android app derives through it), already read it so; its streamed walk was the outlier and moved (io-pimdir b41dd5d). No store holds a row the rule re-derives.
- **A person settles an item conflict** (SYNC §7, normative). An `Edit` without `overrule` on a conflicted item, through any binding of it, gives the item the edit's body whatever it is (its own, the diverging one, or another, a merge among them), clears `conflicted`, releases `conflict_object`, measures no divergence and retains and reports nothing; the editing binding's `shared_object` moves to the body, every other binding's stays, and each source whose base holds another body owes it. "An edit whose object the base holds stages nothing" now says "for its source", since two of the six cells edit to the body the editing binding's base holds and still settle. The write tells the settle from a sync's upsert, which leaves the conflict standing, by the engine stating it, as for an overrule. Guarded by vectors/sync/118 to 123, vector 102's store without `overrule`: through b (the source the item moved away from) keeping c3, taking c2 and writing c4 (card-basic-retitled.vcf, the fourth card, standing for a merge, which io-pimdir's draft vector thought missing), and through a (the source agreeing with the item) the same three. Run against io-pimdir in a scratch copy with these vectors vendored: 118 to 121 fail at 77c8e4c, before its settle, the cells its log names; all six pass at b41dd5d.
- **A store from elsewhere** (STORAGE §18, normative). `PRAGMA trusted_schema = OFF` and `SQLITE_DBCONFIG_DEFENSIVE` are set each where the SQLite offers it, from 3.31 and 3.26, and a setting the SQLite lacks is no deviation. Below 3.31, the 3.18 floor among them, a program SHOULD instead read `sqlite_master` before any other statement, refuse a store holding a trigger or a view whose text the canonical schema at its version does not create, and register no SQL function with a side effect on the connection. checks/floor.sh now pins the premise: SQLite 3.18.2 answers no `trusted_schema`, and stores every trigger's text as the current SQLite does, so the comparison answers alike whichever SQLite created the store. The refusal is a program's behaviour no check here observes.
- **Several statements under one name** (STORAGE §4.4, normative). An implementation's own text for one name MAY be several statements, run in order in one transaction, the caller's or one it opens, keeping the name, parameters, result columns and effect, no other connection's write between them. This is how the Android shape runs the forks of `RETURNING`, upserts and `UPDATE … FROM` on 3.18 (its `Bound.steps`). Program behaviour; checks/ binds the canonical text alone.
- **The one read of `*`** (STORAGE §4.4, normative). A program judging whether it opens a store at all MAY read `store_meta` with `*` in text of its own, taking the columns it knows by name, since the row may be another draft's. checks/schema.sh still refuses `*` in the canonical text, where no statement needs it.
- **Own statement text on the conformance line** (STORAGE §17, normative): `(own statement text)` after the profile, `storage-draft-08 owner (own statement text), sync-draft-07 engine`, in parentheses as SEARCH §12 names a shape, a comma separating parts. Nothing checks a conformance line.
- **Android's no-replace move** (STORAGE §5, informative note): SELinux denies an app `link(2)` on its own data files, so the move there is `renameat2` with `RENAME_NOREPLACE`, a raw system call below API 30.
