# Format identity and versions

Batch 1 of the release audit (cairn/changes/audit-2026-10-31, lines V1 to V6), on the user's decisions of 2026-10-31: drafts are exact, D1 and D3. storage-draft-07 becomes storage-draft-08, sync-draft-07 and search-draft-08 require it, and conventions/gtd.md takes gtd-draft-03 for the versions it requires, no rule of its own moved. Later batches of the audit land in the same drafts.

Rules, and the check guarding each. Every scenario named below was run against the 9606b43 tree (checks/invariants.sh with errexit off, so each reports) and failed there, unless the line says otherwise.

- **Drafts are exact** (STORAGE §4.2, §6 steps 1 and 2; V1). `store_meta.format_version` names the STORAGE version whose schema the store holds, `storage-draft-08` now, `storage-vN` once released, written by `init_store_meta` and followed by `set_store_version`; `load_store_meta` answers it. While draft, every profile refuses a store whose marker is not its own draft's, and a store lacking the column (any draft before 08), naming both versions: never reconciled, migrated, rebuilt, written nor deleted. A released program refuses every draft store. Guarded by invariants.sh, "format: init_store_meta stamps this draft…", "format: a draft's store opens under that draft alone…" and "format: a store an earlier draft wrote lacks the marker, so load_store_meta fails and it is refused", and by checks/names.sh, which fails when the marker `init_store_meta` writes is not STORAGE.md's Status version (on 9606b43: no marker, STORAGE at storage-draft-07).
- **Reconciliation removed** (STORAGE §4.2, §6, §13, §15.3, §15.6, Annex A.1, A, B.2; SYNC §5 step 2; SEARCH §4; V1). §6's step 3, the reconciliation test, its rebuild, repairs, backfills and draft-06 JSON reading, the reader's rules for an older or unreconciled store (a missing column read as `NULL`, a missing table as none), `level` 0, `round_band` on a reconciled store, "`0` before the feed existed", the probes table, a held body stating no mark, a `NULL` `target_collection` from a producer predating it, an intent naming no `source`, the "predating §15.6" clauses of §15.6 and Annex B.2, Annex A's revision history, SYNC's "checkpoint from an earlier draft" and SEARCH's "store from before the feed" are gone, with vector 74's note. Ten statements existing only for reconciliation are deleted: `repair_kinds`, `repair_levels`, `repair_shared_objects`, `backfill_flags_known`, `backfill_base_flags_known`, `backfill_invitation`, `backfill_shared_object`, `backfill_target_collection`, `backfill_task_organisation`, and `backfill_task_capture`, which served revision 1 to 2 alone. `list_held_mail` and `list_held_tasks` stay, for the re-derivation of a later Annex A revision. `store_meta.derivation` loses the default reconciliation gave it. invariants.sh's reconcile and older-reader scenarios go, with their `rebuild()` helper, which failed under SQLite 3.53.3; checks/names.sh drops `legacy_alter_table`, `sqlite_sequence`, `foreign_key_check` and `table_info`, which only reconciliation wrote. The refusal scenarios above replace them.
- **Compatibility versions** (STORAGE §4.2, §6; D1, V2). `store_meta.read_version` and `produce_version` beside `version`: once released an owner opens a store whose `version` it knows, a reader one whose `read_version` is at most its own, a producer one whose `read_version` and `produce_version` both are; while draft the marker governs and the three stay 1. Each migration states what it raises: neither for an index, a table or an ignorable column; `read_version` for a renamed or dropped column or a changed meaning, a value added to a closed vocabulary included (§13); `produce_version` for a `NOT NULL` column without a default on `queue`, `objects` or `collections`, or a new rule on what a producer enqueues. `set_store_version` takes `:read_version` and `:produce_version` and sets the format version to `storage-v` and the version. Guarded by invariants.sh, "versions: a migration stamps the three versions it states…" (failed on 9606b43), "versions: a column added beside the others changes the width of no reader's or producer's row" and "versions: a producer of the version before writes every row it wrote" (both hold on 9606b43, whose statements already named their columns).
- **A statement names its columns** (STORAGE §4.4; V2). No statement, canonical or an implementation's own, reads `*` or inserts without a column list. Guarded by checks/schema.sh, which refuses either in migrations/ and queries/: a seeded `SELECT *` and a seeded positional `INSERT` each failed it; no canonical text broke the rule at 9606b43.
- **One on-disk format** (STORAGE §4.1, §4.3, §16; D3, V3). The 23 tables of 0001_init.sql carry a `CHECK (typeof(…))` per column in place of `STRICT`, naming the declared type and `'null'` where the column is nullable, a key column never (`STRICT` refused a `NULL` key), the rowid aliases exempt, `WITHOUT ROWID` kept. `store_meta.shape`, §4.1's shapes and their refusal, and §6's step 2 are gone; a statement's name, parameters, result columns and effect bind every implementation (§4.4), its text RECOMMENDED. The schema loads on SQLite 3.18; the statements need 3.37 (upserts, `UPDATE … FROM`, `RETURNING`, and `create_param`'s `STRICT` temporary table, which a 3.18.2 run names as the four failures). Guarded by checks/floor.sh, a new flake check (`floor`, Linux only), which builds SQLite 3.18.2 with Android 8.0's flags and source hash from the Android repository's flake, loads 0001_init.sql, compares the 75 objects it creates with those a current SQLite creates, and compiles an insert, an update of every column and a delete for each table with foreign keys on: 9606b43's schema fails at `STRICT`. By schema.sh: no `STRICT` store table (23 at 9606b43), every column its `typeof()` check (removing the one on `objects.size` fails it). By invariants.sh, "types: a value of another type is refused where STRICT refused it…" and "types: a value SQLite converts losslessly is kept, converted", which hold on 9606b43's `STRICT` schema and fail when a check is removed. The proposal's check on 3.18.0 created every table, trigger and index and compiled every write too. SEARCH keeps its own shapes, FTS5 and FTS4; only its references to the store's shape moved.
- **Derivation follows its last writer** (STORAGE §6, Annex A; V4). `set_derivation` sets the revision rather than raising it: an owner at an earlier revision records its own in the transaction of its first summary, address or sort-key write, so the next later owner re-derives. Guarded by invariants.sh, "derivation: an owner at an earlier revision records its own…" (got 3 at 9606b43); the two `list_held_*` scenarios move here unchanged.
- **Durability** (STORAGE §4.1; V5). `PRAGMA synchronous = FULL` or `EXTRA` per connection (MUST); `PRAGMA auto_vacuum = INCREMENTAL`, which 0001_init.sql now sets before its first table, an owner MAY run `PRAGMA incremental_vacuum` after collecting, purging or releasing; `journal_size_limit` RECOMMENDED with WAL; a busy timeout SHOULD for readers and producers, no number stated (Android's build defaults the journal limit to 1 MiB, which the documents leave to the implementation). Guarded by schema.sh, `PRAGMA auto_vacuum` answering 2 (0 at 9606b43, and 0 once the pragma is removed). `synchronous` and the busy timeout are connection settings no check here can observe.
- **Store identity** (STORAGE §4.3, §4.5, §8, §13, §15.4; V5). `store_meta.store_id`, 16 random bytes as 32 lowercase hex digits drawn by `init_store_meta` (`lower(hex(randomblob(16)))`), and `incarnation`, 1 at creation, raised by `raise_incarnation` (new, owner/) past the copy's and the replaced store's when readable; the trigger `store_meta_identity` refuses a changed id or a lowered incarnation. `load_change_cursor` answers both after the stamp and the purge count. A consumer records the four and treats another id, another incarnation or a recorded stamp above the store's as a reset; a producer following a queue id checks the same. Copies: a backup copies pimdir.db through the backup API or `VACUUM INTO`, then objects/, holding the staging lock shared across both so no collection runs between them; a restore raises the incarnation; a live store MUST NOT be replicated by a file-synchronisation tool. Guarded by invariants.sh, "identity: a store draws 32 lowercase hex digits…", "restore: the copy keeps the id, answers another incarnation and a stamp below the one a consumer recorded", "restore: with the replaced store unread, the copy's own incarnation is raised" and "identity: the id never changes and the incarnation never goes down".
- **The index knows its store** (SEARCH §2, §3, §4; V5). `index_meta.store_id` and `store_incarnation`, written by `init_index_meta` from the attached store itself; a refresh rebuilds an index built from another store or incarnation, or whose `store_change` lies above the store's last stamp. `load_index_meta` answers both last. Guarded by invariants.sh, "index: init_index_meta records the store and the incarnation it is built from" and "index: a restored store answers another incarnation than the one the index recorded" (the second failed at 9606b43; the first compares two empty answers there).
- **A rename moves the purge count** (STORAGE §4.5, §13; V6). `collections_restamp_items` also counts the rename in `store_meta.purges`, so a consumer reconciles its keys. Guarded by invariants.sh, "feed: a rename counts in purges, the old keys gone as a purged row's".

Statement signatures that moved: `set_store_version` (`:read_version`, `:produce_version` added); `set_derivation` (no longer conditional); `load_store_meta` (`format_version`, `read_version`, `produce_version`, `store_id`, `incarnation` appended); `load_change_cursor` (`store_id`, `incarnation` appended); `load_index_meta` (`store_id`, `store_incarnation` appended); `init_store_meta` and `init_index_meta` bind what they did. New: `raise_incarnation`. The schema's leading comment follows the draft, as 2026-10-31-the-schema-text-stays-the-tags said it would.
