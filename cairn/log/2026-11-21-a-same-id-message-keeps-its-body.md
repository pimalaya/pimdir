# A same-ID message keeps its body

storage-draft-15 and sync-draft-15, neither tagged, so both are edited in place and no number moves; no migration, a store of this draft keeps no `server_object_id` column and is refused as any other draft's is. The owner's decisions of 2026-11-21 on io-pimdir's cairn/changes/a-same-id-message-keeps-its-body/proposal.md: fix 1 approved, and option (b) for linking. Found by neverest's cairn/changes/a-move-into-a-same-id-message-keeps-both (Stalwart v0.16): two different messages stating one `Message-ID`, one moved into the mailbox holding the other, left the store with one body twice and an item bound to the message whose body it does not hold.

## Rules and the check guarding each

- **A relocation names the member it made** (SYNC §2's delivered create and outcome, §4's new `Remove` bullet, §5's relocated member and push discipline, §6's landing paragraph, §10's ops; STORAGE §14's new `LandPlacement { collection, handle, to, revision }` and the `Superseded` drop it stands for): a connector MAY state, with an accepted `Remove` that relocated, the handle the member now has in `to` (IMAP `COPYUID`, RFC 4315). The engine then lands the destination's create on it in the write recording the outcome, pending or delivered, whatever its key: a `Superseded` drop of the provisional handle, the binding moved, its base the staged flags and body and the outcome's revision. It is never left delivered, so a later listing's other member stating the hint meets a based binding of this source under another handle and is minted apart (§6, today's rule). A stated handle the source already binds in `to` records the create delivered, as without one; without a handle the delivered path stands. Guard: vectors/sync/196-a-relocation-stating-its-handle-lands-the-create-on-it.json (the relocation answering `assigned` 2: the Archive binding lands on 2, base `\Seen` and the staged body); vectors/sync/197-a-listing-after-a-landed-relocation-mints-the-other-message.json pins the follow-up (the next round lists 1, another message agreeing on every listed field, and 2: 2 is matched, 1 minted `dup:basic-1@example.org#1` with seq 2).
- **A server object id decides linking where both state one** (SYNC §2's meta and the new "Server object id", §4's new paragraph "A server object id names content", §6's new paragraph after "Linking instead of fetching", §11; STORAGE §4.3's `bindings` list and column notes, §9's first cross-collection bullet, §14's `lookup_objects(account, source, links)`): a connector MAY state with a member's meta the id its server gives the content (RFC 8474 `EMAILID`, Gmail's `X-GM-MSGID`, JMAP's `Email/id`), never one it derives. The write records it on the binding, `bindings.server_object_id` (TEXT, never empty), a listing stating none clearing it and a fetch stating none leaving it. `lookup_objects` takes the asking `source` and answers beside each holder the id its binding of that source states. An upgrade adopts a body only from a row stating the placement's own id where both state one; where either states none, the §6 agreement alone decides. Guards: vectors/sync/198-an-upgrade-fetches-rather-than-links-a-body-under-another-server-object-id.json (subject, date, sender and size agree, the ids differ: fetched, the twin body kept); vectors/sync/199-an-upgrade-links-a-body-under-an-equal-server-object-id.json (equal ids, linked, nothing fetched); vectors/sync/200-a-listing-records-the-server-object-id-it-states.json (a member stating `M-9` records it, one stating none clears `M-old`); checks/invariants.sh "lookup: each holder answers the server object id its binding of the asking source states, NULL for one stating none or bound by another source alone" (insert_binding, update_binding, load_bindings and lookup_objects).

Statements: `insert_binding` and `update_binding` take `:server_object_id`; `load_bindings` and `load_bindings_by_link` answer it last; `lookup_objects` takes `:source` and answers `server_object_id` last; migrations/storage/0001_init.sql adds the column. queries/signatures.json restated. The two existing lookup expectations of checks/invariants.sh gain the empty last column. generator/src/writer.rs binds `server_object_id` NULL (the generator models no source stating one). New fixture vectors/fixtures/mail-basic-twin.eml: mail-basic.eml with its body's last `.` an `!`, so every listed field agrees and the bytes differ. vectors/schema/sync.schema.json takes `server_object_id` on a binding and a mail member's meta; checks/vectors.py lets a meta state it; vectors/README.md and SYNC §11 say so, and that a relocating remove's outcome may state `assigned`. vectors/manifest.json restated (200 sync cases). GUIDE §9 (push step 7, upgrade step 2) and §10 (server object ids, relocation handles) follow; OVERVIEW names neither.

## Proof that each check fails without its rule

checks/vectors.py checks structure only, so the sync cases were run by io-pimdir's runner over this tree with each rule disabled in a scratch copy of io-pimdir (never through git): the engine ignoring the outcome's `assigned` on a relocation fails 196 alone ("bindings rows differ", the create left delivered under its provisional handle); the upgrade not comparing the ids fails 198 alone (linked); the listing recording no id fails 200 alone. 197 and 199 pass either way: they pin what the rules leave as it was. The invariants scenario fails without the column (`insert_binding` binds a parameter no statement names). Upstream of the fix, the same Stalwart case of neverest fails on its unlisted variant with `COPYUID` dropped and passes with it.
