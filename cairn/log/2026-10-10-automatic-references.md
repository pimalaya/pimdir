# Automatic references by statement, and search reading them

The Android plan's Part C step 5: the C.1 rules recorded the same by every owner, and the search part answering cross-domain queries from the references.

- **Rules are canonical statements** (§14.2), not engine behaviour. The Android app runs the engine in Rust but services every write from Java against Android's SQLite with the canonical statements, so a rule living only in io-pimdir's writer would never run there; a statement runs in both. Recording stays a MAY, and an owner that records MUST record what the statement records. Each rule has a statement per end so whichever lands first is caught by the other: `link_senders_of` and `link_mail_from` (`sender`), `link_invitations_of` and `link_invitations_to` (`invitation`); `attachment` is the stand-in's own (§14.3). A `NULL` link id backfills. Guarded by invariants.sh "auto: a mail refers to the contact its from address names, never through another role", "a contact's backfill takes live mail only", "an address added brings its history, a person's reference kept as it is", "an address removed removes nothing", "a NULL link id backfills every mail", "an invitation refers to the calendar item it names, none for one not held yet" and "a calendar item synced after its invitation is tied to it"; each fails with its role filter, its liveness test or its conflict clause removed.
- **Direction**: from the item whose content states the relation to the item it names, so a mail refers to its sender's card, its event and its attachments. One convention for every rule, read from the mail's side, where the facts are.
- **The statements seek one link id** with `link_id BETWEEN coalesce(:link_id, '') AND coalesce(:link_id, x'')`: one key, or open the whole of `items_by_link`, where `:link_id IS NULL OR …` would scan for every call. Guarded by "auto: <statement> seeks one link id" and "link_invitations_to seeks the invitation".
- **`mail_summary.invitation`** (Annex A.1), the first `UID` of the first `text/calendar` part, with the body: the event side needs it stored, an event often syncing after its invitation is read. Derived from the body only, so the two tiers agree save it; never cleared once read, the message being immutable: `upsert_mail_summary` keeps a known one over `NULL`, which also spares an owner binding no `:invitation` (the Android binder reads a missing name as `NULL`). Indexed by `mail_summary_by_invitation`, partial. Reader statements do not select it, so a reader of an unreconciled store needs no rewrite. Guarded by "auto: a write without the body keeps a known invitation"; summaries.json's "mail, an invitation" case over the new fixture mail-invitation.eml, which checks/vectors.py re-derives through the stdlib parser; every mail row of the vectors gains `"invitation": null`.
- **`linked:`** (SEARCH §8), one operator rather than one per role: `linked:<id>` or `linked:<role>:<id>`, the other ends of the named item's references in either direction, the item named as `id:` names it under every kind it is held. A role names its kinds, so no direction is needed in the query. `linked` reads `store.item_reference` through the attached store; the index copies nothing, a reference being a store fact. `kind:file`, and a file indexed from its summary (its name) whether it holds a body or not. Guarded by vectors/search: the store gains the invitation mail, a file stand-in and three given references, and seven cases (`linked:6`, `linked:invitation:event-series@example.org`, `linked:4` across both accounts, `linked:sender:4` empty, `linked:attachment:8 kind:file`, `linked:10` reversed, `kind:file forecast`); `from:alice@example.org` gains the invitation mail and the coverage the stand-in. checks/vectors.py checks that every given reference's ends are held. Only an implementation runs the cases, and none exists for search yet.
- **No attendee role**: an event's attendees are already its addresses, answered by `attendee:`.
