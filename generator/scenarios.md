# Scenario catalogue

Status: tooling, read once on 2026-11-20 from the consumers' sources

What the consumers of a pimdir store do with it: every queued action each producer issues, every write and read each makes, and every run an engine orders, with the file and line that does it. The generator's profiles draw their events from these rows (README.md, "Events and histories"); a row here is a scenario a sampled history may contain, and the union table at the end is what the producer events must cover.

Read at: himalaya, cardamum, calendula and neverest on io-pimdir 0.18.1, the Android app's rust/ on io-pimdir 0.18.1. Paths are relative to each repository's root; io-pimdir/ prefixes a path in io-pimdir. A consumer's source moves after this reading: a scenario is re-read when its consumer's major lands, never assumed current.

## himalaya (mail CLI)

**Roles.** A reader with the overlay, `PimdirReader::open(root).with_pending()` (src/pimdir/client.rs:68-71), refusing a missing pimdir.db itself (`store-uncreated`, client.rs:58-64); a producer named `himalaya`, opened per command and dropped after its enqueues, bound to the account when the store is grouped (client.rs:35, 119-128); an owner opened by `PimdirStore::open_current` for one call, `drop_action` under `pimdir queue cancel` (client.rs:183-212), refused `store-owned` while a sync holds the lock; a query client, `PimdirIndex::open_query` (src/pimdir/index.rs:234-238), never refreshing. It never drains, purges, collects or writes an item (src/pimdir/backend.rs:10-12).

**Account.** A configured account must be one `accounts_of(None)` answers, any name passing on a store holding no collection; unset, `accounts_of(Some("message/rfc822"))` must answer one account or none, else `store-account-ambiguous` (client.rs:368-405). Mailboxes are the account's collections of kind `message/rfc822` (backend.rs:82, 176-185); an id outside them is refused, so an enqueue never creates a collection (backend.rs:102-120).

**Queued actions.** Built-in actions at `v` 1 (io-pimdir/src/codec.rs:460-540), intents at `v` 1 (io-pimdir/src/intent.rs:535-537). Never issued: `supersedes`, `if_match`, `resolves`, `update`, `calendar-*`, an application's own action. The io-pimdir producer gates every enqueue on STORAGE §15.6; himalaya calls `producer.check` only after a batch failed, to name the refused id (client.rs:106-111).

## cardamum (contacts CLI)

**Roles.** Its network and file backends pull io-pimdir for the query language alone (src/shared/query.rs:9, src/shared/card/search.rs:11) and open no store. The `pimdir` backend is a reader with the overlay (src/pimdir/client.rs:57-58), a producer named `cardamum` opened per write (client.rs:21, 74-84), an owner for `pimdir queue cancel` alone (src/pimdir/backend.rs:413-425), and a query client (src/pimdir/index.rs:93). Address book create, update and delete are refused (backend.rs:463-497). A write into a collection no source syncs is refused `no-performer` (backend.rs:827-840).

**Queued actions.** One action a transaction, `v` 1, `target_collection` `NULL`, never `resolves`, `supersedes`, a performer or an intent; no capability read before the enqueue, the producer's gate deciding (io-pimdir/src/client/producer.rs:597).

| Action | Payload | Body | Triggered by |
| --- | --- | --- | --- |
| `add` | `link_id` derived from the unstripped bytes, `flags` `[]`, `object` (backend.rs:590-603) | stored and pinned, `X-PIMDIR-` lines stripped before the hash (io-pimdir/src/client/producer.rs:331-341) | `card add` (src/shared/card/add.rs:86, 101) |
| `update` | `seq`, `object`, `if_match` the overlay-folded body when the version matches, always on the common path that reads first (backend.rs:616-642; src/shared/card/update.rs:80-92) | stored and pinned | `card update` (update.rs:97, 120) |
| `remove` | `seq`, `if_match` only with `--if-match` (backend.rs:656-687) | none | `card delete` (src/shared/card/delete.rs:49) |

**Bodies.** A minted card carries `UID:urn:uuid:<v4>` (src/shared/card/vcard.rs:113-122); a card from a file passes byte for byte, possibly without a `UID`, with several cards or `X-PIMDIR-` lines (src/shared/card/fields.rs:128-130). A `UID`-less card carrying `X-PIMDIR-` lines gets a `hash:` key over bytes other than the stored body's.

**Reads.** `list_contacts_page_asc` through `list_summaries` with the overlay, by keyset (backend.rs:716-742); a card with no body listed from its summary (backend.rs:1008-1035); `get_item`; `list_refusals`, `count_pending_creates`, `load_parked_actions`, `change_cursor` for `pimdir status` (backend.rs:113-186); the receipt path for `queue show`; the index's search, hits read again with no overlay (index.rs:117-163). Never reads conflicts nor capabilities.

**To generate.** `carddav/default` and bare ids; a `text/vcard; charset=…` kind (it compares the media type alone); an empty name (falls back to the id); UIDs minted, absent, blank, reserved; two cards sharing a `UID` under a minted key; an add over a live holder a pending `remove` withdraws (io-pimdir/src/client/producer.rs:286-292); chains of overlaid updates (`if_match` naming a pending update's object), a delete after an update, a read under a pending remove; an `update` or `remove` over a conflict, parked (it never states `resolves`); a stale `if_match` parked; malformed rows (`pimdir status` failing `action-malformed` until a drain parks them, backend.rs:2492).

## calendula (calendar CLI)

**Roles.** A reader with the overlay, which folds pending updates and removes and not creates (src/pimdir/client.rs:67-72); a producer named `calendula` opened per write (client.rs:36, 89-101); an owner for `pimdir queue cancel` alone (src/pimdir/queue.rs:310-326); a query client never refreshing (src/pimdir/index.rs:139-146). Calendars are the collections of media type `text/calendar`, an undeclared one not listed (src/pimdir/backend.rs:563-576). Calendar create, update and delete are refused (backend.rs:158-178).

**Queued actions.** One action a transaction through one producer, never `enqueue_batch`; never `set-flags`, `move`, `copy`, `set-performer`, the collection intents, `supersedes` nor `resolves`; flags always `[]`.

| --- | --- | --- | --- |

| `update` | `seq`, `object`, `if_match` when given or read by the command, the body local (backend.rs:317-356) | as `add` | `event update` (src/shared/event/update.rs:127-195), `item update` (src/shared/item/update.rs:81-138) |
| `remove` | `seq`, `if_match` with `--if-match` (backend.rs:454-488) | none | `event delete` of a whole series (src/shared/event/delete.rs:53-99), `item delete` |
| `calendar-reply` | `source`, `seq`, `partstat` (`ACCEPTED`, `TENTATIVE`, `DECLINED`), `comment`, `recurrence_id` (io-pimdir/src/intent.rs:412-429) | none, anchored on the item's calendar (backend.rs:741-783, 947-949) | `pimdir reply` (src/pimdir/intent.rs:84-166) |
| `calendar-cancel` | as reply without `partstat` (backend.rs:794-824) | none | `pimdir cancel` |

**Gates.** Before the enqueue: a known collection, a synced one, and for the user's own body an online meeting asked only where a source declares `calendar.online-meeting` (backend.rs:285-442). In the producer's gate: `calendar.item.*`, `calendar.scheduling` for a scheduled body (an attendee not marked `SCHEDULE-AGENT=CLIENT` or `NONE`), `calendar.occurrence.update` when the occurrences differ, `calendar.component.vtodo` for a VTODO (io-pimdir/src/capability.rs:297-332). An intent checks the invitation in a local body (organizer, attendee, an exact `RECURRENCE-ID`) and is queued unchecked when the body is not held (backend.rs:756-813, 1099-1126); its performer comes from `producer.performer`, or the one syncing source when none declares (backend.rs:841-915).

**Bodies.** Minted with `PRODID:-//Pimalaya//calendula//EN`, a v4 UID, `DTSTAMP` and `DTSTART` in UTC (src/shared/ical.rs:241-269); all-day `VALUE=DATE`, floating, UTC, and `TZID` with a `VTIMEZONE` written once (src/shared/event/fields.rs:999-1022, 1351-1390); organizer and attendees `PARTSTAT=NEEDS-ACTION;RSVP=TRUE`, never `SCHEDULE-AGENT` (fields.rs:1229-1265); a display alarm; no `RRULE` nor `RECURRENCE-ID` but from a given source.

**Reads.** `list_summaries` ascending by keyset, pending updates taken store-wide so a stale summary rules nothing out (backend.rs:607-655); a range filtered on the summary for a bodiless item, `dtstart` to `until` for a recurring one (backend.rs:1291-1331); `get_item`; capabilities; `pimdir status` and `queue list` as cardamum's, with the intents (src/pimdir/queue.rs:115-193); the index scoped to events. Its agenda is its own expansion over `list_items` (src/shared/event/agenda.rs:303), never `occurrences_between`.

**To generate.** `caldav/default`, `work/cal` and `home/cal`; undeclared collections; VEVENT, VTODO and VJOURNAL in one collection, a VTODO into a calendar stating `calendar.component.vtodo` none; bodiless, blob missing and unreadable items; two resources sharing a `UID`; floating, all-day, UTC and zoned times, Windows `TZID`s with an inline `VTIMEZONE`, unknown `TZID`s; `RRULE` with `UNTIL`, `RDATE`, `EXDATE`, overrides, one moved outside a window (src/shared/event/expand.rs:1152-1694); a pending update changing an item's kind or `UID`; scheduled bodies gating add, update and remove; calendars with no source, sources declaring nothing, several declared sources with and without a performer recorded.

## neverest (the sync engine, the store's owner)

Read on io-pimdir 0.18.1 at sync-draft-15 (io-pimdir/src/sync.rs:68). The backend tables come from forked readers whose references were relayed, not each reopened. Not in neverest: a watch or IDLE loop (`sync` is one-shot, cairn/spec/sync.md:415), a JMAP connector (configurable, bails at src/account.rs:433-435), a maildir or vdir backend, an eviction or a release below a date.

**Ownership.** Its own `local/sync.lock`, waited on 60 s polled every 500 ms (src/cli/sync.rs:41-51, 589-644), taken without waiting by `--queue-only` (src/cli/queue.rs:57-65); io-pimdir's `owner.lock` failing at once (io-pimdir/src/client.rs:223-250). No migration: a store of another draft is refused with its remedy (src/sync/driver.rs:305-357); `open` re-derives rows of an older Annex A revision (io-pimdir/src/client.rs:244-250). One handle per source, `for_account(account).for_source(source)` (driver.rs:309-315).

**Declaration.** Before the drain (driver.rs:715-720), after each listing (src/sync/driver/local.rs:254-271, pair.rs:156-175) and after the run (driver.rs:686-688), each replacing the source's rows (driver.rs:774-837) from `capability::declaration` (src/sync/capability.rs:87-118): the held-only intents `none` source-wide and per held collection, rename and delete `none` on a collection with a role, a Graph source's `mail.message.add` on drafts alone (capability.rs:126-152), `calendar.component.vtodo` from the taskless calendars it recorded (capability.rs:156-215), every non-intent row `none` under one-way (capability.rs:268). `register_syncing` runs `load_checkpoint` and `upsert_checkpoint` on a connection of its own, outside io-pimdir's owner API, to record a source syncing a collection with no checkpoint (src/sync/storage.rs:143-182).

**One run** (src/cli/sync.rs:289-446): `--init`; per store its lock and `check_store`; `--reset` (refused while rows are queued or parked: `delete_collection` per collection, an empty declaration, `collect_garbage`, src/cli/sync.rs:690-773); `prepare` and declare for every account, then **one store-wide drain** (driver.rs:727-753); per account `driver::run` (driver.rs:505-708): `check_mode`, per source the intents, then a local run or a pair run, a failed source noted and the run going on; `report_parked`, `count_conflicts`; then `declare`, the retention sweep when `store.purge-after` is set (retained items 512 at a time, one `purge_items`, `collect_garbage`, src/sync/driver/upkeep.rs:126-219), the index refresh within `store.index-timeout` (src/sync/index.rs:34-74), the sidecar under local/. `prune_receipts` (7 days) ends every drain (io-pimdir/src/client/producer.rs:1362-1376).

**The drain** (io-pimdir/src/client/producer.rs:1362-1653, through src/sync/driver/queue.rs:27-96): store-wide in append order, runs of 64 rows a transaction and a savepoint a row; a store failure parks, an environment failure retries 5 times then parks; each row applied as the source syncing its collection, gated on the declaration; receipts naming the seq; `set-performer` applied; the intents skipped and counted, parked when the named source declares the capability `none`, untouched at an unknown `v`. It drains once a run, on a dry-run replica, after a merge, after submits that queued a copy, in queue-only and in conflict resolve.

**Intents performed.**

- Collection intents (queue.rs:104-319, 577-635): the named side or the one whose namespace holds the collection, else pending; create, rename, delete on the server; success acknowledged with no seq, a permanent failure parked, a transient one counted and pending; unpaired, a rename followed by `rename_collection` and `set_collection_name` on the collection and its children, a delete by `delete_collection`.
- `submit` (src/sync/driver/send.rs:39-505; src/sync/submit.rs:279-380): an id left in local/submitting parked `unconfirm_action`; one naming another sender parked; per row the attempt counted, a durable in-flight mark, the send, then either `replace_action` with an `add` into the copy collection flagged `\Seen` (where the provider files no copy itself, capability.rs:303-323) or an acknowledgement; on failure pending, parked, `unconfirm_action` (cut after the message was handed over) or held for a quota; a broken channel halts the rest.
- `calendar-reply`, `calendar-cancel` (queue.rs:327-541): the same mark protocol under local/inviting; a seq gone parks; an item not landed yet or still provisional waits; performed by Google Calendar and Graph, any other backend refusing for good.

**What it enqueues itself**: the submit's copy (send.rs:164-176), merged conflict updates (reconcile.rs:487-494), resolved conflict updates (src/conflict.rs:195-203). Never `set-performer`.

Every push error leaves the verb running; an enumerate or fetch error ends it (src/sync/mod.rs:214-241). A refusal is an error coded unsupported or a 4xx other than 401, 407, 408, 409, 412, 423, 425 and 429, never a quota (src/error.rs:282-310).

**Crash points.** A page lands in writes of at most 1,024 ops, each push chunk of 64 is followed by the write of its outcomes, the tail op after the last chunk (io-pimdir/src/sync.rs:451-463, 1435-1540): a kill between pages leaves the round at its cursor, a kill mid-page replays one push chunk at most, the checkpoint is never written early. A rekey writes once, after every page. Each hydration batch is its own upgrade (src/sync/driver/tests.rs:6182). A drain run of 64 commits whole. A submit or an invitation killed after its mark parks unconfirmed on the next run (tests.rs:5630, 1969). A relayed copy killed before its binding is bound on the next pull by its `Message-ID` (tests.rs:5267). A server rename killed before `follow_rename` reads as a new collection. The sidecar save is last: lost, the next run reads the old mode.

**To generate.** A source registered with no checkpoint before any sync; the hub of a one-way pair holding 1+N sources on one collection; a refused cursor answered by a complete page that opens a round; a DAV token rejected into a round; an IMAP source without QRESYNC whose delta is a round's first page; Graph calendar and plain DAV listed whole every run; a band round carrying no checkpoint; Gmail labels as collections sharing one handle space; a submit's copy replacing its row; a merged `update` drained at once and parked when the local body moved; retained items swept on `purge-after` 0.
