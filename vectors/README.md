# pimdir test vectors

Status: informative

Test data for the pimdir standard (STORAGE.md §16, SYNC.md §11, SEARCH.md §11), part of it alongside migrations/, queries/ and payloads/. The conformance tables of STORAGE.md §17, SYNC.md §12 and SEARCH.md §12 say which profile each file binds; this file says how each was made and how to read it. They exist because the values a store fixes are the ones nothing checks: a schema mismatch fails a query, while two writers naming the same body differently produce no error at all, silently never deduplicating and silently never finding the blob the other wrote.

## Files

- **objects.json**: bodies to their BLAKE3 digests and object names, with the path STORAGE.md §5 derives from each, one shard directory deep. Every profile passes it (STORAGE.md §17): object naming is where a disagreement costs data rather than presentation.
- **payloads.json**: queue payloads of every action the documents define, each valid or malformed as its schema under payloads/ says (STORAGE.md §15.3): a member missing, of another type or undefined, `seq` and `link_id` both or neither, a flag twice, a path for a body. checks/vectors.py validates each against its schema, and each schema against the shape STORAGE.md writes for it.
- **summaries.json** and **fixtures/**: bodies to the `link_id`, the summary row, the address rows and the `sort_key` Annex A produces, and for mail the attachment mark read without the body (`meta_attachment`, from the top-level `Content-Type`), and the parts its stand-ins name (`attachments`: section, name, media type and decoded size, STORAGE.md §14.3), every case that annex has to hedge included, and the encodings that split earlier writers (an RFC 2047 header, an escaped vCard value, a quoted parameter). The header parses of Annex A.1 have a case each: a Message-ID without brackets, one that names nothing, comments around the ids, an obsolete two-digit year, an obsolete zone name in a folded and commented Date, a military zone with a three-digit year, no seconds, a day the month lacks, a folded and padded Subject, malformed encoded words beside one in an unknown charset, and raw bytes that are no UTF-8; those stating no Message-ID carry what they pin into their `alt:` key. The line ends of Annex A.1 have three: a closing delimiter cut between its `\r` and its `\n` (mail-cut-delimiter.eml), a header line holding a lone `\r` before its CRLF (mail-stray-cr.eml) and a header cut after its last `\r` (mail-header-cut.eml). The zone resolution of A.3 has a `TZID` the IANA database resolves, a wall time a transition repeats and one it skips. The bounded walk of a message's parts (STORAGE.md Annex A.1, §14.3) has a case at each bound: an attachment at depth 64 beside one at 65, an attachment as the 10,000th entity beside one as the 10,001st, and 1,001 attachments of which 1,000 are stood for. A card states a `KIND` and an `ORG` (card-kind.vcf), an event its organizer and attendees, an `RDATE` and a `DURATION` (event-people.ics), and a journal its own table (journal-basic.ics). Every fixture is a body some case names. An owner passes the cases for each `kind` it writes (STORAGE.md §17).
- **sync/**: one case per file, numbered from 1 with no gap, a store, a run, a remote and what is expected after (SYNC.md §11). Bodies are named by label and resolved to fixtures, so a case reads, and every expected push carries the idempotency key SYNC.md §4 derives. Vector 70 expects the collection, stand-ins and references an owner recording attachments writes as a body enters (STORAGE.md §14.3); vectors 104 and 105 keep two bodies through one binding, and 118 to 123 settle an item conflict by a person's edit, through the source agreeing with the item and through the one it moved away from, keeping its body, taking the diverging one or writing a third.
- **search/**: the fixture store and the queries every conforming index answers alike (SEARCH.md §11), hits keyed `(account, seq)`, a threaded listing's threads, or the refusal a query answers (its code and span), and where a case states `cut`, how many calendar items of its collections were cut before its range's end (SEARCH.md §7, §8.2); the occurrence windows `occurrences_between` lists, row by row in its order; and chunks.json, field texts and the chunk boundaries SEARCH.md §6 cuts them into.
- **schema/**: the JSON Schema (draft 2020-12) of each format below, closed: every object names its members and refuses any other, so a field misspelt or unknown fails validation.
- **manifest.json**: the SHA-256 of every file a vendor copies and the number of cases each case file holds (below).

Two cases pin the fallback keys: event-no-uid.ics the **`hash:`** key Annex A.2 derives for content with no usable `UID`, the FNV-1a 64 digest of the bytes, and mail-no-message-id.eml the **`alt:`** key Annex A.1 derives for a message with no `Message-ID`. card-reserved-uid.vcf pins the **escape** (STORAGE.md §9): a `UID` beginning with a prefix the writer derives keys under is filed under `esc:` and the `UID`. Three of summaries.json's cases pin the **minted** `link_id` (STORAGE.md §9): a hint the collection already holds under another handle is filed under `dup:`, the hint, `#` and the handle, concatenated verbatim in that order, and sync vector 31 pins the same over a fallback. Each reuses the fixture of the case above it, since minting depends on the hint and the handle and never on the body, and each carries the `hint` and `handle` its key was built from, so a consumer rebuilds the key rather than pattern-matching the string.

## Formats

Each file states the version of its format as a top-level integer `v`. A format's version moves when a runner has to read something new to reproduce a case: a field added, removed or given another meaning, a value added to a closed set, bumps it, with its schema's `const`; a field only a reader of the notes uses (a `note`) does not. The current versions: objects.json 2, summaries.json 3, payloads.json 1, sync/ 2, search/store.json 1, search/queries.json 2, search/chunks.json 1, manifest.json 1. sync/ moved to 2 for `narrowed`, `enumerated` and `carries`, and queries.json for `cut`, which earlier drafts added under 1.

A `note` may stand on any case or file and is read by no runner.

### objects.json

`base32` holds the encoder's `alphabet`, its `rfc`, `padding` (false) and `cases`, each an `input_utf8`, its `input_hex` and the `base32` it encodes to. `algorithms` names `blake3` with its `digest_bytes`, `name_chars` and `derivation`. Each of `objects` is a `label`, the body as `body_hex` or as `body_len` bytes of `body_pattern` (byte `i` is `i mod 251`), and under `blake3` its `digest_hex`, its `name` and the `path` STORAGE.md §5 builds.

### summaries.json

`conventions` restates the annex's standing, `fixtures_are_crlf` is true. A case is a `label`, the `kind` (media type), the `fixture` and its `body` (`len` and `blake3` name), the `link_id` it is filed under, for a minted key the `hint` and `handle` it was built from, the `table` and its `summary` row (every column of the table, a task's categories as `categories`, a message's reply ids as `in_reply_to`), the `addresses` (`role`, `position`, `address`, `name`), the `sort_key`, and for mail `meta_attachment` and `attachments` (`part`, `name`, `media_type`, `size`).

### payloads.json

Each case names its `action`, the `payload` and whether it is `valid` under payloads/ (STORAGE.md §15.3).

### sync/

- **Rows**, in `store` before the run and in `expect.store` after it, each list a table of STORAGE.md §4.3 under its own spellings:
  - `collections`: `id`, `account`, `kind` (empty when undeclared), `conflict` (the collection's policy), `generation`, and after a run that declares one its `name` and `role`;
  - `objects`: by label, the fixture a `body` names, `blob` false for a row whose blob file is missing, `corrupt` true for one whose bytes fail its name;
  - `items`: `collection`, `link_id`, `seq`, `flags` (null when unknown), `object` (a label, null when bodiless), `sort_key`, `level` (1 meta, 2 full), `deleted`, `retained` (true when `retained_at` is stamped, its instant unstated), `retained_by`, `conflicted` and `conflict_object`;
  - `bindings`: `collection`, `link_id`, `source`, `handle` (a provisional one written as `\u0001` and the link id, SYNC.md §2), `base_flags` (null when unknown), `base_object`, `base_revision`, `base_present`, `conflicted`, `conflict_revision`, `conflict_object`, `shared_object` and `round`;
  - `sources`: `collection`, `source`, `checkpoint`, the round as `round`, `round_open`, `round_since`, `round_until`, `round_cursor`, `round_checkpoint`, `round_band` and, where a band head reads it, `round_started_at`, and the coverage as `covered` (true when `covered_at` is stamped), `covered_since` and `covered_until`;
  - `summaries`: a `table`, its `collection` and `link_id`, and the `row` columns the case compares;
  - `addresses`, `supersessions` and `references`: the rows of `item_address`, `supersessions` and `item_reference`, their own columns.
- **Run**: its `verb`, `collection` and `source`; an upgrade's `tier` (Meta or Full) and the `handles` it upgrades; `options`: `push`, `rights` (`flags`, `content`, `add`, `remove`), `conflict` (the run's policy), `scope` (`since`, `until`) and `accept_absences`; a mutate run's `mutation`, by `kind`: Add its `object` and `flags`, Edit its `seq` and `object` with `if_match` and `overrule` where stated, Remove its `seq`, SetFlags its `seq` and `flags`, Copy and Move their `seq` and the collection they go `to`.
- **Remote**: one page as `snapshot` or a round's `pages`, a page holding its `items`, the `vanished` handles, `complete`, `last`, `cursor`, `checkpoint`, and on a round a date filter narrowed `narrowed`, its last page the handles an unfiltered enumeration lists as `enumerated`; a member its `handle`, `flags`, `revision`, its `meta` (the fixture as `body`, with the source's own `size` and `attachment` where it states them, or for a file the `link_id` and the `summary` its source states: `name`, `media_type`, `size`, `part`) and `carries` when the listing carries the body (SYNC.md §4); `heads`, the heads the connector lists, and `head`, its answer to the run's head (`kind`, the `from` checkpoint or the `since` instant, then `rejected`, or the head's `items`, `vanished` and `checkpoint`); `fetch`, by handle and by tier (Meta or Full), the `body`, the `revision` and for a file its `meta`; `cursor_rejected`, `interrupted_after` and `scope_bound`.
- **Expect**: the `pushes` in order, each a `kind`, its `handle` and `key`, and by kind what it carries: an Add its `link_id`, `flags`, `origin` (`collection`, `handle`), `object` and `supersedes` (`collection`, `handle`, `if_match`); a Remove its `to`, `link_id` and `if_match`; a SetFlags its `add` and `remove`; an Update its `object` and `if_match`. The `outcomes` fed back (`handle`, `outcome`, an add's `assigned` handle and `revision`), the `events` (`kind`, `handle`, an Overruled one's `link_id`), `parked` with its `absent` and `bound` counts, `failed`, and the rows after.

**Policies** are spelled three ways, one per layer. A collection's `conflict`, a row of STORAGE.md §13, is manual, prefer-incoming or prefer-existing: the policy an engine applies between its sources. A run's `conflict` option is manual, prefer-remote or prefer-local, which SYNC.md §5 writes `Manual`, `PreferRemote` and `PreferLocal`: the run's policy between the store and the one source it syncs, prefer-remote keeping the source's body and prefer-local the store's.

### search/

store.json's `collections` are an `id`, an `account`, a `kind`, a `role` and the `sources` rows giving the coverage (`source`, `covered_since`, `covered_until`, `covered_at`); its `items` a `collection`, `seq`, `link_id`, `flags`, and a `fixture`, or for a bodiless item a `summary` (`table`, `row`, `addresses`, `sort_key`); its `references` the rows of `item_reference`.

queries.json states the `now` relative dates resolve against, the `horizon` (`start`, `end`), the `coverage` (per kind, the bodiless placements a dated answer counts), the `cases` and the `occurrences` windows (`start`, `end`, `rows`). A case is a `query`, an optional `sort` (date, name, relevance) and `ordered` (true when its hits compare as a list), one answer: `hits` as `(account, seq)` pairs, `threads` (`thread`, `count`, `first`, `last`, `hits`), or the `error` of a refusal (`code`, `start`, `end`); and where it states them `horizon_left`, the `temporal` coverage (full, or `since`, `until` and `filling`) and the `cut` count (SEARCH.md §8.2).

chunks.json's cases are a `label`, the `fields` (`body`, `note`, each a list of strings or of a string to `repeat` some `times`) and the `chunks` (`ord`, `field`, `start`, `end`).

### manifest.json

`files` maps each file a vendor copies, every file under vectors/ and payloads/ but this README and the manifest, by its path from the repository's root, to its SHA-256 in hexadecimal. `cases` maps each case file but the sync cases to the length of each list it holds, by JSON pointer (`/cases`, `/base32/cases`), and `sync` counts the sync cases.

## How the expected values were derived

From the algorithm and prose specifications, never by running an implementation. Values taken out of one implementation would record what it does rather than what the format says, and nothing could then meaningfully disagree with it.

- The base32 encoder was written from RFC 4648 §6 rather than taken from a library, and checked against the vectors of RFC 4648 §10, which appear under `base32.cases` so a consumer can check its encoder before trusting anything below.
- The digests are anchored on published values: every body but `abc` and `high-bytes` follows the BLAKE3 project's test-vector input convention (byte `i` is `i mod 251`), so the 0 to 5, 63, 64, 1023, 1024 and 1025 byte cases can be checked against that project's own `test_vectors.json`, the empty digest included.
- Every value of objects.json and summaries.json is reproduced through a second, independent path, which checks/vectors.py re-runs on every push, never a pimdir implementation: `blake3` and `base64` for the names; a header parser written from Annex A.1, not Python's `email` package, whose readings are lenient where the annex is exact, for every column a message's summary reads from a header field, its address rows and its sort key; the standard library's MIME walk within the bounds for the marks and the stand-ins; vCard and iCalendar lines unfolded and split by hand for every column of a card, an event, a task and a journal, their address rows and their keys, a calendar time resolved through the resource's own `VTIMEZONE`, else Python's `zoneinfo` over the IANA database, else as floating, the offset before a transition taken for a repeated or a skipped wall time (A.3). Every UTC normalisation was also reproduced against the tzdb with coreutils `date`, both daylight-saving transitions included.
- The sync and search cases were written from SYNC.md and SEARCH.md by hand, and only an implementation runs one. checks/vectors.py validates their structure and that every fixture, object label and placement they name resolves, and re-derives what a case fixes on its own: every push's key, every refusal and chunk boundary from the prose, a query at and past each limit of SEARCH.md §8.3, the hits of a text term on the title field by SEARCH.md §8.5's compilation over an FTS5 table of the fixtures' titles, and the windows and `cut` counts of the series a simple rule states. It checks the rules a sync case pins whatever an engine does: no `Remove` the consumer did not stage, every Overruled event's key minted over its binding's handle (STORAGE.md §9), the guards that park a round or a rekey, a member disagreeing with a held message minted apart, no body pushed over or left facing a server edit nobody read, and a prefer- policy settling only once both bodies are read. The other expected rows, pushes and hits stand as written.
- Every payload checks/invariants.sh enqueues is valid against payloads/, but the one its comment calls malformed.

## Rules for a consumer

- **Read `v` first.** A consumer meeting a `v` it does not know stops rather than reads the file as the version it knows. checks/vectors.py validates every file against its schema.
- **Compare parsed structures, never JSON text.** Key order is not fixed here, and pinning one would pin an accident of whichever serialiser wrote the file.
- **Read the fixtures as bytes.** They are CRLF throughout, as RFC 5322, RFC 6350 and RFC 5545 require, but for the lone `\r` the three line-end cases hold on purpose, so a harness that opens them in text mode changes the body and therefore the object name. This repository pins them with a `-text` gitattribute, and a consumer that vendors them owes itself the same. Each case carries its fixture's `blake3` name for exactly this reason: check them first, and a mangled read fails there rather than somewhere confusing later.
- **Vendoring is allowed, unchecked vendoring is not** (STORAGE.md §16). An implementation that cannot read this directory from its own build copies vectors/ and payloads/ with manifest.json, and its CI checks the copy against the manifest, `jq -r '.files | to_entries[] | "\(.value)  \(.key)"' vectors/manifest.json | sha256sum -c -` from the copy's root, and the manifest against this repository's at the revision it follows: equal manifests mean an unchanged copy, and its runner counts the cases it ran against `cases` and `sync`, so a case it skips shows. A frozen copy that keeps passing while the format moves is worse than no copy.

## Case folding

Annex A lowercases by the default full mapping of Unicode 15.0.0, locale-independent (Rust's `str::to_lowercase`, Java's `toLowerCase(Locale.ROOT)`, Python's `str.lower`). card-full-lowercase.vcf pins it on the one letter where the mappings part: a dotted capital I folds to `i` and a combining dot above, in the address the sender rule compares (A.6) and in the sort key (A.2). card-casefold.vcf stays ASCII.
